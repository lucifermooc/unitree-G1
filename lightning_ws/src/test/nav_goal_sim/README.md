# Nav2 到点精度仿真（G1 运动学）

在 PC（ROS 2 humble + `ros-humble-navigation2`）上复现"导航报到达、人却停在偏处"，并比较改进方案。不是 colcon 包，直接运行脚本。

## 为什么会偏

`g1_nav_bridge/src/cmdvel_to_sport.cpp` 为了让 G1 能动，会改写 Nav2 的速度指令：

| 指令 | G1 实际执行 |
|---|---|
| 转向（\|wz\| ≥ 0.15） | wz 至少 0.6，**vx 至少 0.2**（不能原地转，走半径 0.22~0.5 m 的圆弧） |
| 前进 vx ≥ 0.05 | vx 至少 0.3（不能慢速蠕动） |
| vx < 0.05 且不转 | 完全停止 |

1. 原来的 SmacPlanner2D 只规划位置，终点朝向与来向不同时只能在终点"原地转"，G1 走成圆弧横移 0.4~0.6 m；
   到点判定 `stateful: true` 在位置第一次进入 0.2 m 时就锁定，所以照样报到达。
2. 到点停车时，速度平滑器按 0.6 rad/s² 慢慢减速，减速段被抬回 0.6 rad/s，停车后又多转 15~27°。

## 文件

| 文件 | 作用 |
|---|---|
| `g1_motion_sim.py` | 模拟 G1：订阅 `/cmd_vel`，套用 cmdvel_to_sport 的抬速规则 + 一阶速度响应，发 `/odom` 和 TF |
| `nav2_sim_params.yaml` | Nav2 参数（humble 写法）。控制器、到点判定、平滑器、半径与膨胀照抄 `aid_navigation2/param/nav2_params.yaml`；代价地图只有静态层 + 膨胀层 |
| `planner_2d.yaml` / `planner_hybrid.yaml` | 规划器：原来的 SmacPlanner2D / 改后的 SmacPlannerHybrid（DUBIN） |
| `decel_fast.yaml` | 速度平滑器快速减速（改后的值） |
| `goal_tight.yaml` | 到点位置容差 0.12 m（试验，未采用） |
| `sim_launch.py` | 起 map_server、planner/controller/smoother/behavior/bt_navigator（行为树用 Thor 的 xml）和 G1 仿真 |
| `run_goal_test.py` | 每个（变体, 场景, 重复）单独起一套仿真，发 NavigateToPose，记录结果和轨迹到 `results/<时间>/` |

## 运行

```bash
sudo apt install ros-humble-navigation2      # 只需一次
source /opt/ros/humble/setup.bash
cd lightning_ws/src/test/nav_goal_sim
python3 run_goal_test.py --reps 2 --jobs 4                       # 全部变体 × 全部场景
python3 run_goal_test.py --variants hybrid+fast --scenarios s1   # 只跑一组
```

## 2026-10-03 结果（每格两次重复：位置误差 m / 朝向误差 °）

| 变体 | s1 事故复现 | s2 朝向与来向一致 | s3 回原点调头 | s4 朝向垂直 |
|---|---|---|---|---|
| 原配置（2d） | 0.36/26、0.35/27 | 0.18/4、0.16/5 | 0.47/23、0.47/23 | 0.39/14、0.35/15 |
| 只换规划器（hybrid） | 0.41/26、0.21/18 | 0.04/6、0.05/9 | 0.28/16、0.31/12 | 0.16/7、0.12/5 |
| 只加快减速（2d+fast） | 0.38/0、0.36/2 | 0.16/2、0.15/2 | 0.42/3、0.42/1 | 0.25/0、0.26/1 |
| **两项都改（hybrid+fast，已采用）** | **0.13/1、0.13/1** | 0.08/5、0.08/8 | 0.20/1、0.22/3 | **0.13/0、0.11/2** |
| hybrid+fast+容差 0.12 | 0.17/2、0.17/2 | 0.03/8、0.03/6 | 0.21/2、0.22/4 | 0.11/2、0.12/0 |

32+8 次全部 SUCCEEDED，到点用时各变体相近。剩下 0.1~0.2 m 是沿进场方向冲过头：
cmdvel_to_sport 把前进速度至少抬到 0.3 m/s，G1 没法慢速靠近终点，停车有距离。收紧到点容差基本没帮助，未采用。

## 局限

- 仿真里的 G1 是理想运动学 + 一阶响应（时间常数 0.25 s），没有步态、打滑和真实的停车距离；绝对误差以实机为准，变体之间的相对好坏可参考。
- 没有传感器障碍层、禁行区；只用 humble 版 Nav2（Thor 是 Jazzy），Jazzy 的参数写法以 `aid_navigation2/param/nav2_params.yaml` 为准。

## Orin 30524 跟线 / 到点仿真（2026-10-25）

无 Thor 背包的 G1（Orin 30524）用实测执行器模型重跑，比较速度桥和 RPP 的改法。

| 文件 | 作用 |
|---|---|
| `g1_orin_model.py` | 纯 Python：速度桥（照 `cmdvel_to_sport.cpp` + 待评估方案）+ G1 模型。每项参数的实测来源写在文件头 |
| `track_offline.py` | 离线快速版（简化 RPP，直线），标定扰动（`--sweep`）、快速比较方案 |
| `g1_orin_sim.py` | ROS 节点：`/cmd_vel` → 桥 → G1 模型 → TF（叠加步态晃动的"定位位姿"）；另发 `/sim/truth`、`/sim/sent` |
| `nav2_orin_rpp.yaml`、`planner_orin.yaml` | Orin 当前导航配置（RPP、容差 0.3 / 0.30、原地转 0.6、inflation 0.85、cost_travel 10） |
| `ctrl_rot09.yaml`、`ctrl_rot09_tol015.yaml` | 方案 B（原地转 0.9）、B + xy 容差 0.15 |
| `sim_orin_launch.py`、`run_track_test.py` | 每个方案起一套 Nav2，在地图 1792839199393 上按实机三个点 (6.00,−0.94)/(10.39,1.02)/(10.37,−1.46) 来回发 |

```bash
source /opt/ros/humble/setup.bash && cd lightning_ws/src/test/nav_goal_sim
python3 -B track_offline.py                     # 离线，几秒
python3 -B run_track_test.py --map <map_dir>/map_sim.yaml --legs 9 --jobs 7 --seed 0   # 真 Nav2，约 6 分钟
```
地图用 Orin `~/maps/1792839199393/map.pgm`；(8.02, −1.07) 有一个孤立占据像素，半径 0.5 m 时把走廊堵死（实机能过），仿真图里删掉了。

模型要点（实测）：走路转向无死区、增益 0.55~0.78；原地转 |wz|≤0.29 不转；原地转逆时针漂移 0.6/0.8/1.0 → 0.22~0.33/0.15~0.20/0.08~0.10 m（转 120°）；
延迟 0.35 s；步态晃动只加在定位位姿上；**走路蟹行 9.5°**（只发 vx 时实际行进方向比机体航向偏左：导航包定位 +9.2°、`/odommodestate` +9.8°，
motion_test 直走 +10.3~11.1°）。扰动（OU 航向角速度 σ 0.10 / τ 5 s）按实机"现状"标定：横向偏差 p50 0.10、p95 0.20、换向每 3~4 s。

**结果**（两个随机种子 × 9 段，横向偏差按定位位姿、只算走路段；到点按骨盆真实位置）：

| 方案 | 横向偏差 p50 / p95 / 带符号均值 | 到点误差均值 | 锁死段数 | collision ahead |
|---|---|---|---|---|
| 现状（抬速 0.32、原地转 0.6、容差 0.3） | 0.105 / 0.25 / +0.11 m | 0.24 m | 1/18 | 110 + 11 |
| wz_stop 0.05 | 0.096 / 0.235 / +0.09 | 0.23 | 2/18 | 73 + 110 |
| A 走路不抬速 | 0.100 / 0.24 / +0.10 | 0.22 | 2/18 | 76 + 96 |
| A+B（原地转 0.9） | 0.103 / 0.25 / +0.11 | 0.20 | 0/18 | 34 + 4 |
| A+B+容差 0.15 | 0.098 / 0.25 / +0.09 | 0.10 | 2/18 | 90 + 113 |
| A+B+航向补偿 9.5° | **0.062 / 0.205 / +0.01** | 0.17 | 0/18 | 9 + 0 |
| A+B+航向补偿+容差 0.15 | **0.065 / 0.19 / +0.03** | **0.08**（最大 0.16） | 0/18 | 4 + 0 |
| A+B+base_link_nav（10°） | 0.064 / 0.19 / ±0.03 | 0.18 | 0/18 | 0 + 15 |
| A+B+base_link_nav+容差 0.15 | 0.068 / 0.195 / +0.01 | 0.10（最大 0.18） | 0/18 | 14 + 0 |

base_link_nav 两行 = `g1_nav_bridge/crab_comp_frame` 的接法（`crab_comp_sim.py` 逐行照搬 `crab_comp.hpp`：g = clamp((|v|−0.10)/0.10)、τ 0.3 s、20 Hz；
只有 local costmap / controller 用 base_link_nav，`local_base_link_nav.yaml`），和"直接改发布航向"等价。

- "一直偏一侧 ~0.1 m"来自蟹行：纯追踪平衡点 = 前视 0.6 × tan 9.5° ≈ 0.10 m，转向死区 / 桥抬速不是主因（A 改不了）。
- 锁死都发生在往西走、蟹行把机器人推向南墙（(7.8,−1.2)~(8.9,−1.6)，离墙 <0.5 m → RPP / Spin 都报 collision）。航向补偿后 0 次。
- 容差 0.15 只有和航向补偿一起才稳；单独收紧会多出锁死。
- 局限：原地转延迟按 0.35 s 算（实测原地起转 0.1~0.2 s），原地转 0.9 时到点航向误差 ~10° 可能偏大；没有传感器层；
  直线模型复现不出实机"wz_stop 0.05 更差"；结果在 `results/track_20261025_204553`、`track_20261025_205025`（不入库）。

## 重规划仿真：规划后才看到的障碍（2026-10-26）

问题：实机路径有时贴着障碍（10-25 21:54 S 弯离南墙 0.43~0.5 m；网页截图里路径起点还在机器人身后，说明是很久以前规划的）。
怀疑旧行为树只在路径进 253 才重规划，规划后才看到的障碍离路径 0.4~0.8 m 时路径一直不变。

| 文件 | 作用 |
|---|---|
| `obstacle_layer_sim.yaml` | 两张 costmap 加一层点云障碍（`/sim/obstacles`），只标 base_link 2.5 m 内（= 实机 STVL 标记距离），只标不清 |
| `sim_orin_launch.py` 的 `costmap_extra` | 叠加到 planner_server / controller_server 的额外参数 |
| `run_replan_test.py` | 场景 × 旧树（提交 51acdfe 的版本，自动取出）/ 新树（加 `PathExpiringTimer 2 s`），Orin 模型 = 当前部署的 A + 原地转 0.9 + 蟹行补偿 |

```bash
source /opt/ros/humble/setup.bash && cd lightning_ws/src/test/nav_goal_sim
python3 -B run_replan_test.py --seeds 0 1 --jobs 6      # 6 场景 × 2 树 × 2 种子，约 4 分钟
```

场景：走廊 3.0 m 宽、16 m 长，路径旁边一个只有传感器看得到的 0.5 m 箱子，近边离中线 0.55 / 0.70 m（半径 0.5），0.45 m（网页半径 0.4）；
两块大障碍夹 2.0 m 通道（截图的形状），障碍画在地图里 / 只有传感器看得到 / 后者 + 半径 0.4。

**结果**（两个种子；离障碍按骨盆真实位置到最近障碍格中心）：

| 场景 | 旧树：规划次数 / 机器人最近 / collision ahead | 新树：规划次数 / 机器人最近 / collision ahead |
|---|---|---|
| 侧箱 0.55 | 1 / **0.65、0.51** / 0、9 | 10~11 / **0.83、0.80** / 0 |
| 侧箱 0.70 | 1 / 0.80、0.70 / 0 | 10 / 0.74、0.81 / 0 |
| 侧箱 0.45，半径 0.4 | 1 / **0.55、0.43** / 0、9 | 11~12 / **0.76、0.86** / 0 |
| 通道，障碍在地图里 | 1 / 0.80、0.78 / 0 | 13~14 / 0.79、0.74 / 0 |
| 通道，只有传感器 | 3 / 0.80、0.76 / 0 | 14 / 0.80、0.72 / 0 |
| 通道，只有传感器，半径 0.4 | 3 / 0.76、0.76 / 0 | 13~14 / 0.81、0.75 / 0 |

- 侧箱：旧树一条路径走到底，机器人从箱子旁 0.43~0.65 m 擦过，2/6 次触发 9 次 collision ahead 停车（= 实机 0.43~0.5 m）；新树看到箱子后 2 s 内改道，0.76~0.86 m，0 次停车。
- 通道（障碍在地图里）：规划器自己走通道中线，弯角处离障碍 0.83 m（膨胀外沿）—— **障碍一开始就在 global costmap 里时规划器不会贴障碍**。
- 通道（只有传感器）：障碍挡住路径 → 路径失效，旧树也会重规划，两者都 0.72~0.80 m。旧树的问题只在"新障碍离路径近但没把它压进 253"时出现。
- 代价：新树单程多 0~4 s，原地转多 0~4 次（侧箱 0.45 / 半径 0.4 种子 0：4 次 vs 0 次）。
- 局限：障碍是理想点云（无遮挡、无噪点）；humble 版 Nav2；没有测动态障碍 / 人来回走时路径左右翻转。结果 `results/replan_20261026_094220`（+ 补跑 `replan_20261026_094556`，不入库）。
